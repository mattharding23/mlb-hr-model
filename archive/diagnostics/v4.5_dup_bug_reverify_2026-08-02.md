## 3. `HOT_SHRINKAGE_K = 40` — still reasonable on corrected data?

**Plain answer: yes, no revision needed.** The curve itself is unchanged (it's a pure
function of `r_pa`, not of the data-fetch bug) — what changes is which part of the curve
real data actually lands on:

| r_pa | w = r_pa/(r_pa+40) |
|---:|---:|
| 10 | 0.200 |
| 20 | 0.333 |
| 35 | 0.467 |
| 55 | 0.579 |
| 90 | 0.692 |

The corrected live range today was **2–69, median 48** (§2a) — comfortably inside the
10–90 span originally used to justify `k=40`, and the median (48) sits almost exactly on
the `r_pa=55` reference point from the original v4.5 curve-check (`w=0.579`), giving
`w≈0.545` today. The one thing the correction changes is that the `r_pa=90` point in the
original table now looks *more* extreme relative to real data than it appeared before (when
buggy `r_pa` commonly exceeded 90 — median was 96) — real 14-day samples essentially never
reach 90 PA even with a doubleheader. That doesn't invalidate `k=40`; it just means the
curve's upper tail (`w=0.69`+) will rarely if ever bind in practice. `k=40` remains a
sensible choice against the true data.

## 4. `s_pa` finding — correction to the prior report

The prior fix report stated only Jake Rogers (BAL) was affected by the `s_pa` undercount,
based on checking for multi-team fragmentation in the **L14-window** `byDateRange` data.
That check was against the wrong window: `s_pa`/`split_adj` comes from the **season-long**
`statSplits` query (`sitCodes=vl,vr`, `season={yr}`, no date range), so a player traded at
*any point this season* — not just within the last 14 days — could hit the same
fragmentation bug. Re-checking directly against `results/picks.json`'s `s_pa` field
(present precisely because of the Step 2 logging fix) surfaces the correct count:

**11 of 299 players (3.7%) had a different `s_pa` before vs. after the fix**, all in the
undercount direction (the old `next()`-based code grabbed one partial team-stint instead of
the season-combined total):

| Player | s_pa (buggy) | s_pa (fixed) |
|---|--:|--:|
| Tyler Heineman | 35 | 93 |
| Luis Rengifo | 38 | 163 |
| Donovan Walton | 87 | 120 |
| Patrick Bailey | 127 | 197 |
| Jonah Heim | 109 | 127 |
| Jacob Gonzalez | 81 | 113 |
| Nicky Lopez | 133 | 136 |
| Elias Díaz | 71 | 77 |
| **Jake Rogers** | **89** | **91** |
| James Outman | 12 | 27 |
| Austin Wynns | 10 | 40 |

Jake Rogers is confirmed as one real case (undercount from 89→91 — a small delta because
his BAL stint contributed only 2 more PA to the relevant sitCode than the partial row the
old code grabbed), but not the *only* one. The largest correction, Luis Rengifo
(San Diego → Milwaukee), was verified directly against the live API: the old code's
`next()` grabbed San Diego's partial vs-RHP split (38 PA) instead of the season-combined
total (San Diego 38 + Milwaukee 125 = 163 PA) — a 4.3x undercount. This is a materially
larger real-world impact than previously reported, and several of §2c's largest `model_prob`
changes trace directly to this correction rather than to the `r_pa` fix.

The fix (`combined_hitting_stat()`, same helper used for both `r_pa` and `s_pa`) handles
this correctly by construction — it isn't specific to Jake Rogers or to any fixed list of
affected players, so no further action is needed beyond the code change already made.

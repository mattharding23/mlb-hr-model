## Step 3 — Rolling L14 window, implemented

**Data source changed:** `get_statcast()` no longer calls `statcast_batter_exitvelo_barrels()`
(a Baseball Savant leaderboard with season-to-date aggregates only, no date-range parameter).
Now calls raw play-level `pybaseball.statcast(start_dt, end_dt)` for the same `d14`/`date` window
`hot_adj` already uses, and aggregates ourselves:

```python
bip = df[df["type"] == "X"]          # batted-ball events
barrels   = (grp["launch_speed_angle"] == 6).sum()   # Savant's own "Barrel" classification code
hard_hits = (grp["launch_speed"] >= 95).sum()
```

**Verified this classification is correct** before trusting it: a live single-day pull
(2026-08-08) gives barrel rate 7.09% and hard-hit rate 34.3% among `type=="X"` rows, closely
matching the model's existing `LG_BARREL=0.067`/`LG_HARD_HIT=0.385` constants — strong sanity
check that `launch_speed_angle==6` and `launch_speed>=95` are the right classification rules
(earlier, incorrect attempt using `launch_speed.notna()` instead of `type=="X"` as the BBE filter
gave a badly wrong hard-hit rate of 21.5%, caught before use — the difference was foul balls with
tracked exit velocity being incorrectly included).

**No by-name fallback.** The raw pull's `player_name` column is the *pitcher's* name (one row per
pitch thrown, not per batter) — unlike the old leaderboard, which had a clean per-batter name
field. `sc_by_id` is now ID-only; `run_model()`'s lookup simplified from
`sc_by_id.get(id) or sc_by_name.get(norm(name))` to `sc_by_id.get(id)`. This should be low-risk —
batter IDs come from the same MLB Stats API roster/lineup data used throughout the rest of the
model, not from Statcast matching — but flagging the removed fallback explicitly since it's a
behavior change, not just a data-source swap.

**`SC_MIN_BBE=3` added** — a minimum batted-ball-event floor before `sc_adj` moves off neutral
(1.0), mirroring `hot_adj`'s `r_pa>=5` gate. Not strictly required for correctness (the
empirical-Bayes shrinkage already degrades gracefully toward 1.0 as BBE→0 — at `n=0`,
`sw=0/(0+100)=0`, so `sc_adj` would compute to exactly 1.0 anyway with no explicit gate), but
added as basic hygiene against near-zero-BBE noise entries (e.g. a pinch-hitter with one batted
ball in the window).

## BBE sample size under the new window

Live check, `pybaseball.statcast('2026-07-28', '2026-08-11')` (60,443 raw pitch rows, 10,531
batted-ball events, 415 batters with ≥3 BBE):

| | Old (season-cumulative) | New (L14 rolling) |
|---|--:|--:|
| Median BBE | ~241 (Bet-tier mean, prior checkpoint) | **26** |
| Range | 56–369 (Bet-tier) | 3–55 (leaguewide) |
| `sw = n/(n+100)` at median | ~0.68 | **~0.21** |

**This is a large, real shift, exactly as flagged when `SC_SHRINKAGE_K` was left unchanged in the
constants block.** At the new median BBE, only ~21% of the raw rate is trusted — 79% is pulled to
league average, versus ~68% trust before. `SC_SHRINKAGE_K=100` was calibrated against the old
season-cumulative BBE distribution (documented in the v4.5 `VERSION_HISTORY.md` entry: 50-BBE
pipeline floor, ~200 half-season, 350+ full-time) and is now being applied to a data source with a
completely different scale. **Not changed this release, per instruction not to retune based on
this check alone** — flagging clearly for the next checkpoint that this constant is now doing
something different than it was designed to do, and is probably over-shrinking a signal that's
actually fresher (14-day-recent) than what it was calibrated against, even though it's a smaller
sample.

## Pin-rate re-check — reported as observation, `SC_GAMMA` not retuned from this

**Same `SC_GAMMA=0.30`/`SC_CAP=1.07`/`SC_FLOOR=0.93`, only the underlying data source changed:**

| | Old (season-cumulative, properly re-derived) | New (L14 rolling, live 2026-08-11 snapshot) |
|---|--:|--:|
| Bet-tier at-cap (n=58) | 86.2% | **32.8%** |
| Leaguewide at-cap | 26.5% (n=1,718, v4.5 tracked pop.) | **4.6%** (n=415, all L14-qualifying batters) |
| Leaguewide at-floor | 13.9% | 0.2% |

**Answering the question directly: the pin-rate drops substantially on its own once staleness is
removed.** Going from season-cumulative to rolling L14 data, holding `SC_GAMMA`/cap/floor fixed,
took Bet-tier binding from 86.2% down to 32.8% — more than half the reduction needed to get away
from the old formula's 94.8% figure came from removing staleness alone, not from the exponent
discount. This suggests `SC_GAMMA` doesn't need urgent further attention at this checkpoint — the
rolling window was doing real, substantial work by itself. 32.8% is still a real, non-trivial
binding rate (roughly 1 in 3 Bet-tier picks still sit at the new, much-lower ceiling), so this
isn't "problem solved" — but it's no longer the near-universal, information-destroying pin the old
construction produced. Per your instruction, not adjusting `SC_GAMMA` based on this number —
reporting it for the next checkpoint's use once live outcome data exists under this construction.

**Caveat on method:** these figures use one live pull as of 2026-08-11 (matching the last
diagnostic/checkpoint date), applied once per player to all of that player's Bet-tier picks in the
window — not a separate 14-day pull ending on each of the ~7 distinct pick-dates in the archived
window. A fully faithful historical reconstruction would need up to 7 different overlapping
pulls. This is the same snapshot-approximation the root-cause diagnostic used for the pre/post-ASB
league-rate check, flagged there for the same reason — the direction and rough magnitude should
hold, but treat 32.8% as directionally reliable rather than a precise historical figure.

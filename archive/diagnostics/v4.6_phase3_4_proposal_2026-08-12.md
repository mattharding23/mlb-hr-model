## Phase 3 — sc_adj / hot_adj interaction rule

**Target failure mode** (from `archive/diagnostics/v4.5_checkpoint_2026-08-11_rootcause.md` §4):
7 cold-tagged (`hot_adj<1.0`) Bet-tier picks, all 0-7, where a static/capped `sc_adj` overrode an
explicit "cooling off" signal. Phase 2 already shrank `sc_adj`'s ceiling substantially (log-odds
max 0.140→0.068) and its data source is no longer stale (season-cumulative→L14 rolling), which
reduces how often this can happen — but doesn't eliminate the underlying disagreement scenario:
a genuinely cold recent stretch (`hot_adj` at its floor) can still coexist with a currently-strong
Statcast reading, and there's no reason to assume Phase 2 alone fully resolves that specific
conflict rather than just making it less frequent.

**Proposed rule:**

```
if hot_adj <= 0.78 and sc_adj > 1.0 and rec == "Bet":
    rec = "—"
```

Mirrors the existing `pitcher_data_missing` downgrade pattern already in `run_model()`
("downgrade Bet picks when no SP or BP stats are available... `if pitcher_data_missing and rec ==
"Bet": rec = "—"`") — same style, same place in the pipeline, not a new mechanism shape.

**Why this specific threshold, not something else:**
- `0.78` is `hot_adj`'s existing hard floor (not a new number) — it's also the exact threshold the
  code already uses for the 🧊 "ice cold" label (`hot_label` block: `hot_adj <= 0.78: "🧊"`). Reusing
  an existing, already-meaningful threshold rather than inventing a new one.
- `sc_adj > 1.0` is the simplest possible "pointing the other direction" test — no new number at
  all, just "positive vs. not."
- Rejected a broader threshold (e.g. `hot_adj <= 0.90`, matching the ↘ "trending down" label) —
  checked whether it was needed and it isn't (see impact check below): the one missed case at a
  broader threshold (Jake Bauers, `hot_adj=0.986`) is barely below neutral, not a meaningful cold
  signal, and a threshold loose enough to catch it would also fire far more often on ordinary
  week-to-week `hot_adj` noise that isn't evidence of a real problem.
- Considered a **soft-damping** alternative (scale `sc_adj`'s log-odds contribution by some
  fraction instead of a hard downgrade) and a **symmetric mirror rule** for the opposite direction
  (`hot_adj` very hot + `sc_adj` near its new floor). Rejected both: soft damping adds a second new
  number (the damping fraction) with no data to size it from, where the hard downgrade needs none;
  the mirror case has no observed failure instance to justify it, and Phase 2's floor tightening
  (0.78→0.93) already sharply limits how much a bad Statcast reading can drag down an otherwise-hot
  player, so the analogous risk is much smaller to begin with. Not designing for a scenario with no
  evidence behind it.

**Historical impact check** (old `sc_adj`/`hot_adj` values, v4.5 Bet-tier population, before
Phase 2's changes — the same data the failure mode was diagnosed from):

| | |
|---|--:|
| Bet-tier picks the rule would have blocked | **6 of 58** |
| Of those, how many were losses | **6 of 6** (100%) |
| Of those, how many were wins (false positives) | **0** |
| Of the 7 known cold-tagged 0-7 picks, how many caught | **6 of 7** (misses Jake Bauers, `hot_adj=0.986`, not a floor case) |
| Full resolved population matching the *condition* (not just Bet-tier) | 422/1,806 (23.4%) — mostly Skip-tier picks where the rule is a no-op since they were never going to be "Bet" anyway |

Zero false positives against the known historical sample, catches 6 of 7 target cases exactly.
The 23.4% population-level match rate looks large in isolation but is irrelevant on its own — the
rule only *does* anything when a pick was already headed for "Bet," which is a small fraction of
that population.

**What this doesn't do:** doesn't touch `sc_adj`'s value itself, doesn't affect any pick where
`hot_adj`/`sc_adj` agree (the overwhelming majority), and doesn't change the pitcher-data-missing
downgrade it's modeled after. Purely a Bet-tier gate for one specific, evidenced disagreement
pattern.

## Phase 4 — league_adj

**Design requirements** (from the original spec): trailing short window (14-30d) vs. a long
rolling reference (60-90d, not season-to-date), uniform across all picks, independent of any
individual player's stats, capped, logged daily regardless of value.

**Windows proposed: short=14 days, long=90 days**, both trailing and ending on the same date
(`date`), sliding forward daily — structurally can't reproduce the ASB-staleness bug this release
exists to fix, since neither window is anchored to a fixed calendar point.

- **Short=14 days:** matches `hot_adj`'s existing window exactly, reusing the same `d14`/`date`
  variables already computed in `main()`. Flagging one nuance: `hot_adj`'s 14-day choice was
  originally motivated by *individual-player* sample-size noise (a single batter gets ~4 PA/game,
  so 14 days ≈ 40-50 PA — already a small sample, the reason `hot_adj` needs empirical-Bayes
  shrinkage at all). A *league-wide* aggregate doesn't have that problem — even 14 days pools
  thousands of PA per day — so 14 days isn't required here for noise-avoidance the way it is for
  `hot_adj`. Proposing it anyway for simplicity and codebase consistency (one fewer date variable,
  reuses infrastructure already validated for Phase 2's rolling Statcast window) rather than a
  sample-size argument specific to this factor.
- **Long=90 days** (top of the suggested 60-90d range): chosen for stability — smooths across
  roughly a third of a season, consistent with the conservative-by-default posture the rest of this
  release has taken (round `SC_GAMMA`, park-anchored `SC_CAP`, etc.). Early-season dates without a
  full 90 days of season history would clamp the long window's start to Opening Day rather than
  reaching into the prior season.

**Data source:** same `teams/stats?stats=byDateRange&group=hitting` endpoint (summed across all 30
teams) already used and validated in the root-cause diagnostic's pre/post-ASB league-rate check —
2 API calls per run (one per window), fully independent of any per-player fetch.

**Cap — checked against real data rather than picked from the suggested range blind.** Pulled the
actual L14-vs-L90 HR/PA ratio at 8 biweekly checkpoints this season (first date with a full 90-day
lookback, 2026-06-24, through 2026-08-11):

| Date | L14 rate | L90 rate | Ratio |
|---|--:|--:|--:|
| 2026-06-24 | 3.573% | 3.003% | 1.190 |
| 2026-07-01 | 3.357% | 3.047% | 1.102 |
| 2026-07-08 | 3.390% | 3.146% | 1.078 |
| 2026-07-15 | 3.536% | 3.166% | 1.117 |
| 2026-07-22 | 3.472% | 3.223% | 1.078 |
| 2026-07-29 | 2.931% | 3.151% | 0.930 |
| 2026-08-05 | 2.743% | 3.178% | 0.863 |
| 2026-08-11 | 2.843% | 3.200% | 0.889 |

**Observed range: 0.863–1.190 (−13.7% to +19.0%)** — wider than the spec's suggested ±10-15pp
range at the top end. Two honest options: cap tighter than what's actually been observed (±15%,
would have clipped the 06-24 point), or cap a bit wider (±18-20%) to avoid clipping what looks like
ordinary in-season variation rather than an obvious outlier stretch. **Proposing ±15%** (`league_adj`
clipped to `[0.85, 1.15]`) — matches the spec's own suggested ceiling, and a cap that binds
occasionally (roughly 1 of these 8 checkpoints) rather than never is consistent with how `SC_CAP`
was reasoned about in Phase 2 (a real, occasionally-binding constraint is the goal, not a
never-triggered decorative one). Noting the coincidence that `ln(1.15)=0.140` matches the *old*
(now-retired) `sc_adj` cap exactly — not a design driver, just flagging so it doesn't look like an
unexplained echo of a prior number.

**Applied as:** a single log-odds addend, computed once per run (not per-player):
```
league_adj = clip(short_rate / long_rate, 0.85, 1.15)
log_odds += log(league_adj)   # same additive form as every other factor
```

**Logging:** proposing a new top-level field in `picks.json` (not nested under `factors`, since
it's identical across every pick in a given run) — `league_adj`, `league_short_rate`,
`league_long_rate` — written on every pick regardless of whether `league_adj` is near 1.0, so a
future checkpoint has a full track record rather than only seeing entries when it did something
visible.

**Independence check:** derived entirely from league-wide team aggregates, zero dependency on any
individual batter's own stats — doesn't touch `hot_adj`'s or `sc_adj`'s inputs, so no double-
counting risk with either, satisfying the original design note.
